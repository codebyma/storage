type과 interface, 무엇이 다른가

props 타입을 정의할 때 둘 중 무엇을 써야 하는지 헷갈릴 때 보는 노트입니다. 같은 코드를 나란히 놓고 차이가 생기는 지점만 짚습니다.

먼저 결론

props 하나를 정의하는 일이라면 둘 다 됩니다

컴포넌트가 받는 값의 모양을 적는 용도로는 type과 interface가 거의 똑같이 동작합니다. 차이가 생기는 곳은 세 군데입니다.

1. 다른 타입을 이어받는 문법이 다릅니다 (extends 대 &).

2. 같은 이름을 두 번 쓰면 interface는 합쳐지고 type은 에러가 납니다.

3. "sm" | "md" 같은 유니온은 type으로만 쓸 수 있습니다.

같은 모양

객체 모양은 두 방식으로 똑같이 씁니다

type은 이름에 =를 붙이고, interface는 = 없이 바로 중괄호를 엽니다. 받는 쪽 컴포넌트 코드는 완전히 같습니다.

type
type ButtonProps = {
  label: string;
  disabled?: boolean;
};
interface
interface ButtonProps {
  label: string;
  disabled?: boolean;
}
어느 쪽으로 정의해도 받는 코드는 동일
const Button = ({ label, disabled }: ButtonProps) => (
  <button disabled={disabled}>{label}</button>
);
차이 한눈에

할 수 있는 일을 표로 비교합니다

할 수 있는 일typeinterface
객체 모양 정의가능가능
다른 타입 이어받기&로 합침extends
같은 이름 다시 선언에러자동으로 합쳐짐
유니온 "sm" | "md"가능불가능
튜플 [string, number]가능불가능
string 같은 기본 타입에 별명 붙이기가능불가능

정리하면 type이 표현할 수 있는 범위가 더 넓고, interface는 객체 모양 전용이면서 합쳐지는 성질이 있습니다.

차이 1

다른 타입을 이어받는 방법

공통 props를 만들어 두고 거기에 몇 개만 더하는 일은 자주 합니다. 결과는 같고 문법만 다릅니다.

type&로 합치기
type BaseProps = {
  id: string;
  className?: string;
};

type CardProps = BaseProps & {
  title: string;
};
interfaceextends로 잇기
interface BaseProps {
  id: string;
  className?: string;
}

interface CardProps extends BaseProps {
  title: string;
}

button의 기본 속성(onClick, type 등)을 그대로 물려받을 때도 같은 패턴입니다.

type
type ButtonProps =
  React.ComponentProps<"button"> & {
    variant?: "primary" | "ghost";
  };
interface
interface ButtonProps
  extends React.ComponentProps<"button"> {
  variant?: "primary" | "ghost";
}

같은 이름의 속성이 서로 다른 타입으로 겹치면, extends는 그 자리에서 바로 에러를 알려 줍니다. &는 에러 없이 합쳐서 쓸 수 없는 타입(never)을 만들 수 있어서, 문제를 나중에 발견하기 쉽습니다.

차이 2

같은 이름을 두 번 쓰면 생기는 일

interface는 같은 이름으로 다시 선언하면 두 선언이 하나로 합쳐집니다. 이를 선언 병합이라고 합니다. type은 같은 이름을 두 번 쓸 수 없습니다.

interface합쳐짐
interface User { name: string }
interface User { age: number }

// User는 { name, age } 둘 다 가짐
type에러
type User = { name: string };
type User = { age: number };
Duplicate identifier 'User'.

type 쪽에서 나오는 에러입니다. "이미 같은 이름이 있다"는 뜻입니다.

병합은 라이브러리가 정의한 타입에 내 속성을 덧붙일 때 쓰는 기능입니다(예: window에 전역 값 추가). 컴포넌트 props에서는 쓸 일이 거의 없고, 오히려 다른 파일에서 같은 이름을 우연히 또 쓰면 에러 없이 조용히 합쳐져 버리는 점이 함정입니다.

차이 3

유니온은 type으로만 씁니다

버튼 크기처럼 "정해진 값 중 하나"를 타입으로 만들려면 type이 필요합니다. interface는 객체 모양만 만들 수 있기 때문입니다.

type Size = "sm" | "md" | "lg";          // type만 가능
type Pair = [string, number];            // 튜플도 type만 가능

type ButtonProps = {
  size?: Size;                           // props 안에서 가져다 씀
};

props의 모양 자체가 유니온인 경우(예: 링크 버튼이거나 일반 버튼인 컴포넌트)도 type으로만 표현됩니다.

고르는 기준

실무에서는 이렇게 정합니다

어느 쪽이 정답이라기보다 한 프로젝트 안에서 하나로 통일하는 것이 가장 중요합니다. 섞어 쓰면 읽는 사람이 매번 "이건 왜 interface지?"를 생각해야 합니다.

  • 유니온, 튜플이 필요하면 그 부분은 type입니다. 그래서 type 하나로 통일하는 팀이 많습니다.
  • 외부에 공개하는 라이브러리 타입이라 사용자가 속성을 덧붙일 수 있어야 하면 interface를 씁니다.
  • 컴포넌트 props는 어느 쪽이든 문제없습니다. 팀 컨벤션을 따르세요.
  • 섞어서 쓰게 되더라도 객체 모양은 interface, 그 밖은 type처럼 규칙을 정해 두면 헷갈리지 않습니다.
연습 문제

interface로 바꿀 수 없는 것은?

아래 세 가지 중 interface로 바꿔 쓸 수 없는 것을 모두 고르세요.

// A
type Size = "sm" | "md" | "lg";

// B
type CardProps = { title: string; price: number };

// C
type Pair = [string, number];
정답 보기

A와 C입니다. A는 유니온, C는 튜플이라 interface로 표현할 수 없습니다. B는 평범한 객체 모양이라 interface CardProps { title: string; price: number }로 바꿔도 똑같이 동작합니다.

정리

기억할 다섯 가지

  • 객체 모양 정의는 type과 interface 둘 다 같은 결과를 냅니다.
  • 이어받기는 type이 &, interface가 extends입니다.
  • 같은 이름을 다시 선언하면 interface는 합쳐지고 type은 에러입니다.
  • 유니온과 튜플은 type으로만 만듭니다.
  • 무엇을 쓰든 한 프로젝트 안에서는 기준을 정해 통일합니다.
